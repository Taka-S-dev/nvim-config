==============================================================================
この nvim 設定の使い方                                                   *cfg*

キー、パネルの中の操作、検索のコツ、C の読み方、SVN をまとめたもの。
入れ方、マシン間の同期、困ったときの対処、設計の理由は README.md にある。

機能ごとの早見                                                  *cfg-features*

この設定で足した機能と、その主なキーの一覧。右端のリンクの上で `<C-]>` を押す
かダブルクリックすると、その機能の説明へ飛ぶ(戻るのは `<C-t>`)。パネルの中の
キーは、パネルで `?` を押すと出る。

右に出るパネル(ジャンプスタック・ピン・トレース・ハイライト単語・コールツリー)
は一度に 1 つ。どれかを開くと、右に開いていたほかのパネルは閉じる(2 つ並ぶと
画面全体の高さが半分になり、下半分が空いたため)。ジャンプスタック・ピン・トレ
ース・ハイライト単語は、閉じても中身が残っていて、もう一度キーを押せば同じ中身
で開く。コールツリーは、次に開くときにカーソルの位置から作り直す。左のファイル
ツリーはそのまま。

  `<leader>jp` ピーク(小窓で読む。窓の中の `m` で横へ寄せ、`gd` で定義へ戻る)
  右クリック → Peek definition / Jump to definition

よく使うキー / コマンド早見                                         *cfg-keys*

記法: `<leader>` は Space、`<C-x>` は Ctrl+x、`<A-x>` は Alt+x。

------------------------------------------------------------------------------
ファイル・バッファを開く                                           *cfg-files*

`<leader>ff`              ファイル名で検索 (Find File)
                          パスをそのまま貼ってもよい。`\` 区切り、先頭の `/`、
                          `C:\…` の絶対パスも、`/` 区切りの相対パスに直して探
                          す。末尾に `:行番号` があれば、その行で開く
`<leader>fg`              プロジェクト全体を grep (Find by Grep)
`<leader>fr`              最近開いたファイル (Recent)
`<leader>fb`              開いているバッファ一覧
`<leader>fo`              コピーした「パスと行番号」を、その行で開く。
                          `a/b.c:456` `a/b.c l456` `a/b.c(456)` `a/b.c#L456`
                          `a/b.c line 456` `a/b.c 456行目` などの書き方を読む
                          (`:OpenPath {文字}` で直接渡すこともできる)。パスは
                          そのまま、今のフォルダから、プロジェクトの根元から、
                          の順に探す。見つからなければ、パスの終わりの部分で
                          ファイルを検索した一覧を出す(途中から書かれたパスで
                          も選べる)。開いた位置からは `<C-o>` で戻れる
`<leader>fl`              今のファイルを左のファイルツリーに出す(ツリーをそこま
                          で開いて、カーソルを合わせる。閉じていれば開く)。ツ
                          リーを開いている間は、ファイルを切り替えるたびに自動
                          でついていくので、スクロールして見失ったときに使う
`<leader>e`               左サイドにファイルツリー表示/トグル
`<C-Left>` / `<C-Right>` (ツリー内)
                          ツリーの幅を 5 桁ずつ狭める / 広げる
`Ctrl`+ドラッグ (ツリー内)
                          ツリーの幅をマウス位置に合わせる
`<S-h>` / `<S-l>`         前 / 次のバッファに切替
`<leader>bd`              現在のバッファを閉じる

作業ディレクトリを移す                                               *cfg-cwd*

`<leader>ff` や `<leader>sg` は、開いているファイルから判定したプロジェクトの
ルートを対象にする。`.git` も `GTAGS` もない場所のファイルでは、作業ディレクト
リ (cwd) が対象になる。大文字の `<leader>fF` と `<leader>sG`、`:grep`、ターミ
ナルは、常に cwd を基準にする。

`:pwd`              今の cwd を表示する
`:cd %:h`           今のファイルのあるフォルダへ移る
`:cd -`             直前の cwd へ戻る
`<C-c>` (ツリー内)  カーソル位置のフォルダを、今のタブの cwd にする (`:tcd`)
`.` (ツリー内)      ツリーの表示をカーソル位置のフォルダに絞る。cwd は変わらな
                    い
`<leader>fp`        過去に開いたプロジェクトから選んで移る
`:LazyRoot`         今のルートと、その判定の根拠を表示する

`nvim some\dir` のようにフォルダを 1 つ渡して起動した場合は、そのフォルダが
cwd になる。エクスプローラの「送る」でフォルダを渡した場合も同じ。

オプション: フォルダを絞り込んで選ぶ外部のピッカー(端末に選択画面を描き、選ば
れたフォルダを標準出力に書くプログラム)を使って、cwd を移せる
(`lua/taka/cd_picker.lua`)。使うピッカーは、マシンごとに
`lua/config/local.lua` の `vim.g.cd_picker` で指定する(書式は `cd_picker.lua`
の冒頭)。指定がない環境や、そのプログラムが入っていない環境では、下のコマンド
とキーは定義されず、ほかの機能にも影響しない。

`:C [絞り込み語]`、`<leader>fd`
                          cwd の下のフォルダを選んで移る
`:C -`                    直前の cwd へ戻る
`:Cf [絞り込み語]`        ファイルを選び、そのファイルのあるフォルダへ移る
`:Zi [絞り込み語]`、`<leader>fD`
                          zoxide の履歴から選んで移る

ユーザー定義のコマンドは大文字で始まる。小文字の `:c` と `:cf` は標準コマンド
(`:change`、`:cfile`)の略なので、上書きしていない。

`<C-w>q`             現在のウィンドウを閉じる
`<C-w>=`             全ウィンドウのサイズを均等に

コードジャンプ(gtags / ctags / LSP 共通)                            *cfg-jump*

`<C-]>` または `Ctrl+クリック`
                          定義へジャンプ
`<C-o>`                   ジャンプ元へ戻る(VS Code の戻る相当)
`<C-i>`                   進む
`<C-t>`                   定義へ飛ぶ前の場所へ戻る(下のジャンプスタックを 1 段
                          戻る)
`<leader>jy`              ジャンプスタックを右のパネルに開く / 閉じる
`gd` (LSP)                LSP 経由の定義ジャンプ
`gr` (LSP)                参照一覧
`K` (LSP)                 カーソル下のドキュメント表示
`<leader>co`              シンボルアウトライン (Aerial) を開閉 — 関数/マクロ/
                          構造体一覧
`<leader>cO`              シンボルナビゲーションのポップアップ

`<A-Left>` / `<A-Right>` も戻る / 進むに割り当ててあるが、ターミナル側が Alt+
矢印をペイン移動などに使っている環境(WezTerm 等)では届かない。`<C-o>` /
`<C-i>` を基本にする。

gtags 専用の機能(呼び出し元の検索など)はレガシー C ナビゲーション(|cfg-c|)を参
照。

                                                              *cfg-jump-stack*
ジャンプスタック(`<leader>jy`、`lua/taka/jump_stack.lua`)は、定義や参照へ飛ん
で潜っている途中の段を、デバッガの呼び出し履歴のように 1 行ずつ積み上げて見せ
る。中身は vim のタグスタック(`<C-]>` で積まれ、`<C-t>` で戻るもの)で、gtags
のジャンプも、ctags のジャンプも、LSP の定義・参照(`gd` など)も同じスタックに
積まれるので、言語を問わず使える。各行は、そこから飛んだ場所と、その行を囲む関
数の名前(treesitter で取る。C で `#ifdef` のせいで構文が読めない関数は、1 桁目
の`{` と `}` から探す)と、飛んだ先の名前(`→ 名前`)。一番下の行は、最後に飛んで
着いた場所。`<C-t>` で戻った段は、次に飛ぶまで薄い色で残る(vim がそう持ってい
る)。いまいる段には、デバッガと同じ黄色の矢印(``)が付く。まだ一度も飛んでいな
くても、空のパネルが開く。`<C-t>` 以外(`<C-o>` やクリック)で前の段に戻ってから
飛ぶと、その段から下を捨てて飛び直しとして積む。同じ場所から同じ名前へもう一度
飛んでも段は増えず、定義の行でその名前に `<C-]>` を押しても積まない。右端の場
所は、ファイルのあるフォルダ(モジュール)ごとに色が変わる(`JumpStackModule1`〜
`5`)ので、別のモジュールに入ったところが分かる。

クリック                  その段の場所を、コードの窓に出す。カーソルはパネルに
                          残り、スタックは変わらない
`Enter`                   その段の場所へ移る。スタックは変わらない
ダブルクリック / `<C-t>`  その段まで戻る(`<C-t>` を何段分か押したのと同じ)。
                          `<C-t>` で戻って薄くなった段なら、そこまで進み直し、
                          矢印とスタックの位置も戻る
`m`                       いまの段を、入れ子のピンとして保存する(ピンのパネル
                          `<leader>jo` で見られる)。辿った経路を残したいとき
`X`                       スタックを空にする(カーソルは動かない)

脇に出すパネル(ピン、コールツリー、ジャンプスタック)は、罫線と、描き直してもカー
ソルの位置を保つ処理を `lua/taka/lib/sidebar.lua` で共有している。

------------------------------------------------------------------------------
調べた道筋をコードの上でたどる                                     *cfg-trace*

大きなコードで不具合の経路や、仕様の問い合わせに答えるための処理の流れを調べた
結果を、手順ごとに「場所・見出し・解説」として書いたファイル(トレース)を、コー
ドの上に重ねて読む(`lua/taka/trace/`)。
トレースは人が書いても、調べる道具に書かせてもよい。ソースには一字も書き込まず
(SVN や git の作業コピーは汚れない)、解説は画面の上だけに出る。

コードの中では、各手順の行に次のものが出る。

- 行番号の左に、手順の番号
- その行の上に、見出しの 1 行。行と同じ字下げで、メモは全部同じ紙の色(付箋の
  ような暖かい色)の地に出る。番号は種類の色の札(原因は赤、怪しい所は黄、結論
  は緑、ほかは青)で、色が意味を持つのは札だけ。左端の縦線は、紙の色の濃い版で
  メモの始まりを示す
- 選んでいる手順(パネルや `]n` で最後に選んだもの)だけは、見出しの下に解説も
  出て、行に色が付く。解説は紙の色の四角いカードになる(背景の無い斜体の文字で
  は、どこまでが解説かがコードと見分けにくかったため)。ほかの手順は 1 行だけ
  で、見出しは同じ紙の色の地に少し暗い文字で出る(背景の無い薄い斜体だとコード
  のコメントと紛れたため)。解説があれば末尾に `…` が付く。全部の手順に解
  説を出すと、手順の多い関数では行の間が解説で埋まってコードが読めなくなるた
  め。長い解説は窓の幅で折り返す

`<leader>ja`              パネルを開く / 閉じる。右に手順が木の形で並ぶ(子の手
                          順は、どの手順から分かれたかの下に付く)。トレースを
                          まだ開いていなければ、今のプロジェクトで一番新しいも
                          のを開く
`<leader>jA`              保存されているトレースの一覧から選んで開く(`:Trace`
                          も同じ。`:Trace {file}` でファイルを直接開く)。一覧
                          の中で `<C-x>`(一覧側なら `dd`)で消す。トレースは
                          ファイルで、消すと戻せないので確認が出る(`Tab` で印
                          を付けたものはまとめて消せる)。各行には見出しの横に
                          トレースの名前(ファイル名)が出る。`y`(入力欄では
                          `<C-y>`)で `Trace "名前"` をコピーして、書いた人や道
                          具に「このトレースの続き」と頼むときに貼る。一覧に出
                          るのは今のプロジェクトのトレースだけで、`<A-a>` で全
                          部のプロジェクトのものを出す / 戻す(題名にどちらか
                          が出る)。今のプロジェクトのトレースが 1 つも無けれ
                          ば、全部のプロジェクトのものから始まる
`:TraceCheck [file]`      トレースを検査する(ファイルを省くと一番新しいもの)。
                          読めない行、ファイルや行番号の欠けた手順、重複した
                          `id`、無い親、ファイルが無い手順、`text` が指している
                          行に無い手順(どの行にあるかも出す)を一覧にする
`]n` / `[n`               次 / 前の手順へ移る(パネルの並び順)
`<leader>jn`              カーソルの行の手順(無ければ選んでいる手順)の見出し
                          と解説を書き換える(下を参照)
`<leader>uR`              解説を全部出す / 全部隠す。隠すと、コードの上の見出し
                          とカードが消えてコードだけになる。行番号の左の手順番
                          号は残るので、どこが手順かは分かる(ピンのメモを隠す
                          `<leader>uN` と同じ)

パネルの中のキー:

`j` / `k` / クリック      その手順を隣の窓に表示する。カーソルはパネルに残るの
                          で、上から順に下りるだけで経路を読める
`Enter` / ダブルクリック  その手順へ移る(カーソルもコードへ)
`N`                       全部の手順のカードを開く / 選んでいる手順だけに戻す。
                          一覧として読み通したいときに
`K`                       その手順の見出しと解説を小窓で見る(言語サーバーのホ
                          バーと同じ。カーソルを動かすと閉じる)。`<leader>uR`
                          でコードの上の解説を隠したまま、解説だけ読める
`r` / `<A-e>`             その手順の見出しと解説を書き換える(`<leader>jn` と同
                          じ。ピンのパネルでメモを直すキーと同じ)
`y` / `<C-y>`             その手順をコピーする(`Tab` で印を付けた手順はまとめ
                          て)。`Trace "名前" step 5/18: 見出し (場所:行)` の形
                          で、書いた人や道具に「この手順をもっと詳しく」と聞く
                          ときに貼る
`Y`                       トレース全体を Markdown でコピーする。結論の手順があ
                          れば最初に「Answer」として出し、そのあとに全部の手順
                          を場所と解説付きで並べる(枝は字下げ)。原因・怪しい・
                          結論・書き換えた手順には `[cause]` などの印が付く。問
                          い合わせへの回答の下書きや記録に貼る
`R`                       読み直す(ふだんは自動。下を参照)
`t`                       ほかのトレースを選ぶ
`X`                       トレースを片付ける(コードの表示を全部消し、パネルを
                          閉じる)
`q`                       パネルを閉じる(コードの表示は残る)

行の右端は場所。ファイル名は、上の行と違うファイルのときだけ出し、同じファイル
が続く行は `:222` のように行番号だけにする(同じ名前が並ぶと見出しの幅を取り、
見出しが切れていたため)。ファイル名の出ている行が、別のファイルへ移ったところ。
絞り込みの文字を打っている間は、間の行が隠れるので全部の行に出す。場所は 1 色
で、色は手順の種類(と見つからない行の警告)にだけ使う。
原因の手順には虫の印、怪しい手順には ? の印、結論の手順にはチェックの印が付く。

トレースは `stdpath("data")/traces/` に置く(Windows では
`%LOCALAPPDATA%\nvim-data\traces\`)。調べているプロジェクトの中には置かない
(作業コピーを汚さず、誤ってコミットもされないように。ピンと同じ)。どのプロジ
ェクトのトレースかは、見出しの `root` で分ける。今のプロジェクトは、今のファイ
ルの上で `GTAGS`・`.git`・`.svn` のあるフォルダ、無ければ cwd(ファイルが cwd
の外ならファイルのフォルダ)。`root` がそれと同じか、どちらかがもう一方の中にあ
れば、そのプロジェクトのトレースとみなす。1 行が 1 手順の JSON Lines で、拡張
子は `.jsonl`。書かれている途中でも、そのまま読める:
>json
    {"title": "SRTP の拡張で落ちる経路", "root": "C:/src/openssl"}
    {"id": "e", "file": "ssl/statem/extensions_srvr.c", "line": 120,
     "text": "...", "title": "拡張を読むところ",
     "note": "use_srtp があるとここに来る"}
    {"parent": "e", "file": "ssl/d1_srtp.c", "line": 60,
     "title": "len の計算", "note": "...", "kind": "cause"}
<
(1 手順は 1 行に書く。上は読みやすいように折ってある。)

`line` の無い行      見出し。`title` がパネルの題名、`root` が相対パスの起点
                     (無ければカレントディレクトリ)
`file` / `line`      場所(必須)。絶対パスでも `root` からの相対でもよい
`title`              パネルと、コードの上の 1 行目に出る見出し
`note`               解説。改行入りの文字列か、文字列のリスト
`kind`               `cause`(原因)、`suspect`(怪しい)、`answer`(問い合わ
                     せへの結論。その振る舞いが決まる行に置く)。無ければ普通
                     の手順
`text`               その行に書いてあること(行全体か、8 文字以上の一部)。
                     書いておくと、行番号の行がそれと違うとき、近くから同じ
                     ことが書いてある行を探し直す。空白の違いは無視する
`id` / `parent`      `parent` に別の手順の `id` を書くと、その下に付く。無け
                     れば最上位に、書いた順に並ぶ。字下げされた手順は親の行
                     から潜って見たもの（読んだら親に戻る）。本筋と並行する
                     別の線は字下げせず、本筋の後ろに並ぶ

見出しと解説の書き換え: `<leader>jn` かパネルの `r` で、手順の見出しと解説を
自分の言葉に直せる。小さな窓が開き、1 行目が見出し、空行のあとが解説になってい
る。普通のバッファと同じに書き換えて `:w` で保存して閉じ、`q` で保存せずに閉じ
る(変更があれば確かめる)。直した手順には見出しの後ろに鉛筆の印が付き、ファイ
ルのその手順の行に `"edited": true` が残るので、書いた人や道具がそのトレース
の続きを調べるときに、そこは読む人が直した言葉だと分かる。

`text` は、コードがトレースを書いた後で変わったとき(編集や `svn update` で行
がずれたとき)と、行番号が書き間違えられていたときの備え。ピンが行の中身で探し
直すのと同じ考え方。どこにも見つからない手順は、番号と場所が警告の色になり、見
出しの後ろに `(line not found)` が付く(違う行を黙って指さないため)。`text`
の無い手順は、書かれた行番号のまま出る。

読めない行や、ファイル・行番号の欠けた手順は、その手順を飛ばして表示し、「何行
読めなかった」と 1 度だけ知らせる(`:TraceCheck` で中身が分かる)。改行で終わっ
ていない最後の行は書いている途中とみなし、何も言わずに待つ。書く側は、同じ検査
を nvim を開かずに実行できる。結果は標準出力に出て、問題の数が終了コードにな
る:
>
    nvim --headless -c "lua require('taka.trace').check_and_exit([[file]])"
<
トレースのフォルダは、ファイルが変わったときだけ OS から知らせを受けて読み直す
(何度も見に行くことはしないので、何もしていない間は何も動かない)。書き足され
た手順は、その場でパネルとコードに増える。`<leader>jA` で選ばずに開いている間
は、今のプロジェクトの新しいトレースのファイルができると、自動でそちらに切り替
わる(別のプロジェクトのトレースでは切り替わらない)。

ssh で入っているときは、`y` でコピーしたものが、接続先ではなく手元の PC のクリ

複数の単語を同時にハイライトする                                   *cfg-words*

`/` や `*` は 1 語しか光らせられない。ループの 3 つの変数をそれぞれ別の色で光
らせておくと、関数を読み下すときに見失わない(`lua/taka/words.lua`)。

`<leader>hh`              カーソルの単語(ビジュアルモードなら選択範囲)を、空い
                          ている色で光らせる。カーソルの所がすでに光っていれば、
                          そこに見えている色を消す(光らせた単語の中に、さらに
                          選択範囲を光らせて重なっているときは、上に見えている
                          後から光らせた方)。6 色まで
`<leader>hn` / `<leader>hp`
                          光っているどれかの単語の、次 / 前の出現箇所へ
`<leader>hc`              全部消す
`<leader>ho`              右にパネルを開閉する。開いているファイル全部の中で、
                          光っている単語が出てくる場所を、検索結果と同じ木の形
                          で一覧にする: 単語(その色、件数)→ ファイル(件数)→ 行
                          (行番号と本文。一致した部分だけ単語の色)。行で Enter
                          かダブルクリックすると、そこへ飛ぶ(パネルは開いたま
                          ま)。単語やファイルの行で `h` / `l` は閉じる / 開く、
                          Enter は切り替え。`dd` でその単語を消す。単語を光ら
                          せたり消したりしたときと、ファイルを開いたり閉じたり
                          保存したりしたときに、一覧は追従する

単語は大文字小文字を区別して、単語全体で一致する(`len` は `buflen` に一致しな
い)。選択範囲は、その文字列のまま一致する。光らせた単語は、別のファイルを開い
ても、ウィンドウを分割しても、消すまで全部のウィンドウで光ったまま。パネルはほ
かのパネルと同じ右側に出る(右のパネルは一度に 1 つ。|cfg-features|)。

                                                               *cfg-selection*
範囲を選んでいる間は、選んだ文字列と同じものが、画面の中のほかの場所でも薄く光
る(VS Code の選択範囲のハイライトと同じ、`lua/taka/selection_matches.lua`)。
マウスのドラッグで選んだときも同じ。大文字小文字を区別して文字どおりに照らし合
わせるので、`[17]` のような記号も正規表現にならない。光るのは `v` で選んだ 1
行の中の、2 文字以上で空白だけではない選択に限る(行をまたぐ選択や `V` での行選
択は、編集のための選択なので光らせない)。選ぶのをやめると消える。`<leader>hh`
と違って、残しておくための色付けではない。色は、LSP がカーソル下の語の参照を光
らせる色(`LspReferenceText`)と同じ。

差分のどこが違うかを帯で見る                                        *cfg-diff*

左右に並べて比べている窓(SVN のログ、`<leader>vd`、git の差分など、`diff` モー
ドの窓すべて)の右端に、幅 2 マスの帯が出る。WinMerge の場所ペインと同じ役目で、
ファイル全体を窓の高さに縮めて、どこに違いがあるかを示す
(`lua/taka/diff/map.lua`)。

右の列    緑: この側にだけある行。琥珀色: 変わった行。赤: 相手側にだけある行
明るい帯  いま窓に見えている範囲(左の列が一番明るい縁)。スクロールについてくる

帯をクリックすると、その位置へ移る(変更のある所なら、その変更の行へ)。相手側に
だけある行も数に入れて縮めるので、左右の帯は同じ高さに同じ違いが並ぶ。帯は窓の
右端から 1 桁内側の 2 桁に重なるので、そこにある文字は隠れる。右端の 1 桁を空
けているのは、窓の境界線をドラッグして幅を変えるときに、帯を掴んで飛んでしまわ
ないようにするため。比べるのをやめると帯も消える。差分は、変更のない部分も折り
たたまずに全部出す(WinMerge と同じ)。折りたたむと、何百行も離れた変更が画面で
は隣り合い、帯の位置と食い違うため。変更から変更へは、帯のクリックか `]c` /
`[c` で移る。

画面の下には、カーソルのある変更のかたまりを出すペインが出る(WinMerge の差分ペ
インと同じ役目、`lua/taka/diff/pane.lua`)。ペインは上下 2 段で、上に左の版、
下に右の版が、それぞれの見出し(ファイル名)の下に並ぶ。片側にしかない行は、もう
片方に「(no line on this side)」の空き行が入るので、上下の同じ高さに同じ位置の
行が並び、片方をスクロールするともう片方も付いてくる。折り返すので、長い行の右
端の変更も横にスクロールせずに見える。各行は、相手側の同じ位置の行と単語単位で
比べて、変わった単語ごとに、差分と同じ琥珀色になる。1 行に変更が 2 か所あれば
2 か所に色が付き、その間の変わっていない部分には付かない
(`out->state = STATE_CHUNK_0;` と `out->te = fffff;` なら `state` と
`STATE_CHUNK_0` だけ)。日本語は 1 文字ずつ比べる。上の左右の差分でも、行の中の
変更は文字単位ではなく単語単位で色が付く(`diffopt` の `inline:word`)。削除され
た行のすぐ下(`]c` が止まる所)では、消えた行のかたまりを出す。変更のない行では、
その 1 行を出す。ペインの高さは、最初は画面の 3 割(上下で半分ずつ)で、中身のか
たまりが変わっても変わらない。境界線のドラッグや `Ctrl+W` の `+` / `-` でペイ
ンの高さを変えると、上下の段が同じだけ伸び縮みし、その高さを覚えて次のペインに
も使う。長いかたまりはペインの中でスクロールできる。カーソルを動かす(帯のクリ
ック、`]c` など)とペインも追いかける。`<leader>uP` でペインだけを閉じ、もう一
度押すとまた出す(ペインの中の `q` は、比較そのものを終える)。比べるのをやめる
とペインも消える。

比べている画面は、どの窓(左右の差分、下のペイン、SVN のログ一覧)でも `q` で終
わる(`lua/taka/diff/quit.lua`)。SVN のログのタブならタブごと閉じ、
`<leader>vd` や gitsigns の差分など、ファイルとその版を並べた比較なら版の側の
窓を閉じて、ファイルの窓は比較をやめてそのまま残る(git の index の側に書き戻し
ていない変更があるときは、その窓も閉じずに残す)。ファイルどうしの比較
(`nvim -d a.c b.c` など)なら、両方とも比較をやめて残る。比べている画面の外では、
`q` は今まで通りマクロの記録に使える(比べている画面の中では、マクロは記録でき
ない)。

左右の窓は、どちらをどう動かしても一緒にスクロールする。nvim 標準の連動は、カー
ソルのある窓でコマンドを使ったときにしか働かないので、カーソルのない側をマウス
のホイールで回したときや、なめらかスクロールの途中でも、もう片方が追いつくよう
にしている(`lua/taka/diff/scroll.lua`)。カーソルも同じ行にそろう。差分の窓で
は、なめらかスクロール(snacks.scroll)を切って、一気に移るようにしている。少し
ずつ動くと、もう片方の窓と帯が 1 コマ遅れて追いかけ、カクついて見えるため
(`lua/plugins/snacks-scroll.lua`)。

絞り込みテクニック                                           *cfg-grep-narrow*

ファイル種別で絞る: snacks picker は `<pattern> -- <ripgrepの追加引数>` 形式で、
`-- ` 以降がそのまま ripgrep に渡される。`--` の前後に半角スペース必須。

>
    my_func -- -t c            # C 言語タイプ(.c と .h の両方。rg --type-list で一覧)
    my_func -- -g *.c          # 拡張子グロブ
    my_func -- -g !test/**     # test 配下を除外(! 否定)
    my_func -- -g src/**       # src 配下のみ
    my_func -- -g src/**/*.c   # src 配下の .c だけ(2 条件は 1 つの glob にまとめる)
    my_func -- --no-ignore     # .gitignore を無視して全部探す
    my_func -- -i              # 大小区別なし
<

引用符を付けないこと。ピッカーはシェルを経由せず、入力を自前で分割して ripgrep
に直接渡すため、`-g "*.c"` と書くと引用符ごと glob として扱われ 0 件になる。
`:grep` コマンドは cmd.exe を通るが、cmd.exe は `*` を展開しないので、引用符が
あってもなくても同じ結果になる。つまり引用符なしの書き方に揃えておけば、どちら
でも動く。

書き方      `<leader>/`(ピッカー)  `:grep`(コマンド)
`-t c`      動く                   動く
`-g *.c`    動く                   動く
`-g "*.c"`  0 件になる             動く

`-g` は 1 つの引数しか取らない。`-g *.h ssl/**` と書くと `ssl/**` が検索対象パ
スとして扱われて破綻する。また複数の `-g` は AND ではなく OR なので、
`-g *.h -g ssl/**` は「.h またはssl/ 配下」で件数が増える。「ssl 配下の .h」は
`-g ssl/**/*.h` と 1 つにまとめる。

`*` と `**` の違い: `*` はディレクトリ区切り `/` をまたげず、`**` は何階層でも
またげる。openssl ツリーの .h ファイル 264 個で数えると `**/*.h` は 264 個、
`*/*.h` は 31 個(ちょうど 1 階層下)しか一致しない。迷ったら `**` を使う。なお
`/` を 1 つも含まないパターン(`*.h`)はファイル名だけで判定され、階層を問わない。

glob は検索の基準ディレクトリからの相対パスで判定される。`<leader>/` は Root
Dir 版なので、`.git` の無いツリーでは基準が意図とずれることがある。
`ssl/**/*.h` が 0 件になったら、基準が既に `ssl/` の中にある可能性が高い。
`:pwd` で確認するか、cwd 基準の `<leader>sG` を使う。

索引ファイルとバックアップは検索対象から外してある: `tags`・`GTAGS`・`GRTAGS`・
`GPATH`・`cscope.out`・`ctags.out` と、`*.BAK`・`*.bak`・`*~` は、どの検索でも
除外される。ctags の `tags` はテキストなので、外さないとシンボルごとに索引の行
(数百桁)が結果に混ざり、バックアップは元ファイルの一致をそのまま重複させる。除
外の一覧はリポジトリ直下の `ripgreprc` にあり、nvim が `RIPGREP_CONFIG_PATH`
でそれを指すので、`:grep`・ピッカー・`<leader>sr` のすべてに効く。足したいもの
は `ripgreprc` に 1 行足す。マシンに既に `RIPGREP_CONFIG_PATH` が設定されてい
ればそちらが優先される。

よくあるパターン: 関数定義だけを探す

>
    ^static\s+.*my_func\(   # static 関数の定義
    ^\w+\s+\*?my_func\(     # 戻り値型 + 関数定義
<

ファイル名で絞ってから中身:

1. `<leader>sg` で grep → 多すぎる
2. `<C-q>` で quickfix に送る
3. `:Cfilter pattern` で quickfix をさらに絞る(`:cdo` で一括編集も可)

レガシー C ナビゲーション (gtags + cscope_maps.nvim)                   *cfg-c*

clangd を当てづらいレガシー C プロジェクト向けに、定義ジャンプ・呼び出し元検索
を gtags (GNU Global) で実現している。LSP 不要・ビルドシステム不要・古い C 方
言でも動く。検索はすべて `global` を直接・非同期で呼ぶので、待ち時間があっても
操作は止まらない。検索のたびにステータスラインの右側にスピナーと
`gtags: <探しているもの>` が出て、答えが来ると
`gtags: SSL_new  18 ms (global, 1 found)` のように所要時間と出所(`global` =
`global.exe` を起動した / `memory` = 前に引いた結果を返した)と見つかった件数に
変わり、2 秒で消える。gtags で見つからず ctags の tags を探したときは、続けて
`ctags: SSL_new  1 ms (1 found)` が出る。見つからなかった名前は覚えず、次も
`global` に聞き直す(索引の作り直し中などで一度だけ空が返っても、nvim を再起動
するまで見つからないままにならないように)。

色分け                                                         *cfg-c-colours*

C のコードは、名前の種類ごとに色を分けている(`lua/plugins/colorscheme.lua`)。
ヘッダー(`.h`)も C として開く(`lua/config/options.lua` の `c_syntax_for_h`。
nvim は既定で C++ として開くが、C++ のパーサーは入れていないので、ヘッダーには
色が付かなかった)。tokyonight のままだと、関数・型・組み込みの型・`NULL`・
`#include` が似た 4 色の青になり(型と `NULL` は同じ色)、呼び出しと型が見分けに
くいため。

関数                      青
型(`int` などの組み込みの型も)
                          黄
マクロ(定義している所も、使っている所も)
                          薄い赤
enum の値、`NULL`         橙
構造体のメンバー          青緑
引数、ローカル変数        色なし

文法だけでは、大文字の名前がマクロか enum の値か分からず、関数のように呼ぶマク
ロ(`MAX(a, b)`)は関数と同じ色になる。そこで、名前がどこで定義されているかを 2
か所で調べて、使っている所の色を分けている(`lua/taka/c_macros.lua`)。

- 開いているファイルの `#define` と enum の値
- プロジェクトに ctags の `tags` があれば、そこに記録された種類(マクロか enum
  の値か)
- `tags` で分からなかった名前は、GTAGS があれば `global` に聞き、定義している
  行が `#define` ならマクロとする。gtags だけで索引したプロジェクトでも、ヘッ
  ダーのマクロ(postgres の `Assert` や `RelationGetNumberOfAttributes` など、
  関数のように呼ぶもの)が分かる。enum の値は、定義の行(enum 全体が 1 行のこと
  も、値だけのこともある)からは確実に見分けられないので、gtags からは判定しな
  い(大文字で書いた enum の値は、どのみち橙になる)。`global` は一度に 1 つだけ、
  画面に出た名前をまとめて(最大 200 個)聞き、GTAGS の無いファイルでは起動しな
  い

索引(`tags` と GTAGS)に聞くのは大文字を含む名前だけ。小文字のマクロ(`min` など)
を索引から拾うと、ほかのファイルにある同じ名前の変数まで色が変わるため。どちら
にも見つからない大文字の名前は、橙のまま。マクロと enum の値の両方として定義さ
れている名前(`enum { A }; #define A A`)は、マクロの色にする。調べるのは画面に
見えている行だけなので、長いファイルでも重くならない(1 万行のファイルで、再描
画 1 回あたり 0.2 ms)。編集して増えた `#define` は、打つ手が 0.3 秒止まったと
ころで読み直す。`#ifdef` で無効になっている部分を灰色にするのは、マクロの値ま
で分からないとできないので、していない。

`<leader>ji` は、gtags が include 関係を索引しないため `#include "foo.h"` の行
を文字列として探している。cscope にある「この変数への代入」と「この関数が呼ん
でいる関数一覧」(callees)は、gtags には無いが、それぞれ代入の一覧(|cfg-writes|)
とコールツリー(|cfg-call-tree|)が出す。

                                                                  *cfg-writes*
代入の一覧(`<leader>jw`、`lua/taka/writes.lua`)は、カーソル下の名前に値を入
れている所を、プレビュー付きの一覧に出す。gtags にはこの情報が無いので、
ripgrep で名前が出てくる行を集め、そのうち構文の上でその名前に書き込んでいる行
だけを残す。コメントや文字列の中の `x = 1`、比較の `x == 3`、添字として読んで
いるだけの `a[x] = 5` は出ない。`s->x = 4` と `.x = 7` は、メンバー x への書き
込みとして出る。同じ名前のメンバーと変数は、行だけではどちらか決まらないので、
区別せずに両方出す。`memset(&x, ...)` のように、ポインタを渡した先での書き込み
は出ない。`#ifdef` のせいで構文が読めない関数の中の代入も出る。openssl で、
13,000 行に出てくる `s` でも 2 秒ほどで一覧になる。

                                                                *cfg-complete*
C の入力補完(`lua/taka/gtags/complete.lua`)は、C には言語サーバーが無いので、
GTAGS から候補を出す。名前を 2 文字打つと、プロジェクト全体の関数・マクロ・型・
enum の値などが出る(`global -c` と `global -cs`)。開いていないファイルのものも
出る。

`->` か `.` を打つと、その前の式の型のメンバーが出る。`a->b.c[i]->` のようにつ
ないでも、配列の添字があってもよい。先頭の変数の型は、カーソルのある関数の引数
とブロックの中の宣言、ファイルの宣言、ほかのファイルのグローバル変数の順に探す。
typedef は 10 段までたどり、構造体の中身は `global -d` が示すファイルを
treesitter で読む。名前の無い struct や union のメンバーも出る。メンバーは、そ
のファイルでよく使われている順に並ぶ。ポインタに `.` を打って選ぶと、`.` は
`->` に直る。メンバーが分かっているときは、開いているバッファの単語やスニペッ
トは出さない。

型の分からない式では何も出さない(間違った候補を出すより出さない)。キャスト
`((T *)p)->`、関数の戻り値、`(*p).`、マクロがそれにあたる。型は宣言から読むの
で、clangd のような正確さは無い。clangd のように補完を出す言語サーバーがつなが
っているバッファでは、こちらは何も出さず、言語サーバーに任せる。言語サーバーが
止まれば、またこちらが出す。

                                                                     *cfg-lsp*
GTAGS の無いファイル(Go や Lua など)で、言語サーバーがつながっているときは、
gtags のキーが言語サーバーに聞く。Go なら `:LazyExtras` で `lang.go` を有効に
すると gopls が入り、そのまま次のように使える。

`<C-]>` / `<leader>jg`    定義へ飛ぶ。タグスタックに積むので `<C-t>` で戻れ、
                          ジャンプスタックにも出る
`<leader>jp`              定義をピークの小窓に出す
`<leader>js`              参照の一覧
`<leader>jc`              呼び出し元の一覧(呼び出し階層を持つサーバーのとき)
`<leader>jh` / `<leader>jH`
                          コールツリー(呼び出し階層を持つサーバーのとき。
                          lua_ls は持たない)
`<leader>jt` / `<leader>jf`
                          テキストとファイル名の検索。GTAGS の索引を使わずに、
                          ファイルを直接探す
補完                      言語サーバーに任せる。GTAGS の補完(|cfg-complete|)は
                          C と C++ だけ

代入の一覧(`<leader>jw`)と `<leader>ji` は C の構文と `#include` を読むので、C
以外では使えない。`<leader>jw` は代わりに参照の一覧(LazyVim の `gr`)を案内する。

                                                                    *cfg-pins*
ピンは、何段も関数を追った後で戻りたくなる場所に、自分の言葉のメモを付けて残す
ためのもの。マークは 26 個までで理由を書けず、ジャンプリストには通った場所が全
部入る。ピンはプロジェクト(`GTAGS` か `.git` のあるディレクトリ)ごとに、nvim
のデータディレクトリ(`stdpath("data")/pins/`)に保存され、ソースツリーには何も
作らない。ピンは行の内容も覚えているので、ファイルが編集されて行がずれても、同
じ内容の一番近い行に着地し、記録も追従する。行の横の印も同じで、ファイルを開い
たときと保存したときに行の内容で探し直すので、エディタの外で(`git pull` などで)
行がずれた後でも、印は今その行がある場所に出る。

パネル(`<leader>jo`)は、ファイルツリーと同じ作りのサイドバーで、画面の右に出る
(左にはファイルツリーがあり、snacks は同じ側のサイドバー 2 つを上下に積んだも
のとして高さを半分にするので、左右に並べると画面の下半分が空く)。上に絞り込み
の入力欄、下にピンの木が並ぶ。ジャンプしても開いたままになる。子のピンは、ファ
イルツリーと同じ補助線(`├╴` `└╴` `│`)で親につながる。最上位のピンには補助線を
引かない(ファイルツリーのプロジェクト名にあたる、線の出どころになる行がないた
め)。印は、しおりの形で統一してある。子のないピンは 1 枚のしおり、子を持つピン
は重なったしおりで、開いている間は輪郭だけ、閉じている間は塗りつぶしになる(フ
ォルダの開閉と同じ考え方)。どの行にも同じ幅の印があるので、同じ階層のメモは同
じ桁から始まる。各行は、左にメモ、右端にファイル名と行番号を表示する。右端に寄
せてあるので、パネルの幅やメモの長さに関係なく、場所は必ず見える(メモが長すぎ
るときに隠れるのはメモの末尾)。関数名はパネルには出さず、`<leader>jM` の一覧に
出る。絞り込みは、パネルでも関数名に一致する。

入力欄(`/` か `i` で移る)に文字を打つと、メモ・行の内容・関数名・ファイル名で
絞り込まれる。絞り込みは、ファイルツリーと同じく木の形を保つ: 一致したピンが、
それがぶら下がっている親のピンと一緒に表示され、一致しない枝は消える。閉じてい
るピンの下も探す。あいまい検索ではなく、打った文字列を含むものだけが一致する。
絞り込みの間は、並べ替え・階層の変更・開閉は無効になる(入力欄を空にすると戻る)。
ジャンプ、メモの編集、削除は、絞り込みの間も使える。

パネルの中のキー:

`Enter`            そのピンへジャンプ(パネルの隣のウィンドウで開く)
`K` / `J`          同じ階層の中で、1 つ上 / 下と入れ替える。下にぶら下がってい
                   るピンも一緒に動く
`>`                すぐ上のピンの子にする
`<`                1 段外に出す(親のすぐ後ろに並ぶ)
`h` / `l`          下にぶら下がっているピンを閉じる / 開く(`za` で切り替え)。
                   閉じた状態は保存される
`r`                メモを編集
`dd` / `<C-x>`     削除。1 個なら確認なしで消えるので、続けて消せる(`u` で戻せ
                   る)。`Tab` で印を付けたピンがあれば、それをまとめて消す。2
                   個以上をまとめて消すときだけ、確認が出る。子を持つピンを消
                   すと、子は消えずに 1 段外へ出て、消したピンの位置に残る
`u` / `<C-r>`      元に戻す / やり直す。対象は削除・並べ替え・階層の変更・メモ
                   の編集・ピンの追加。まとめて消したピンは `u` 1 回で全部戻る。
                   履歴は nvim を閉じるまで
`Tab` / `<S-Tab>`  ピンに印を付けて次 / 前の行へ(ファイルツリーやほかのピッカー
                   と同じ)。`<C-a>` で全部に印
`q`                パネルを閉じる

コールツリー                                                   *cfg-call-tree*

`<leader>jh` はカーソル下の関数を呼んでいる関数を、`<leader>jH` はその関数が呼
んでいる関数を、右のパネルに木の形で出す(`lua/taka/call_tree/init.lua`)。カーソル
下の語が関数でなければ、カーソルのある関数から始める。最初は 1 段だけを出し、
枝は開いたときに初めて調べるので、どこからでも呼ばれる関数でも、開いた分しか時
間がかからない(postgres の `palloc` は、呼び出し元 757 個が 5 秒ほどで出そろい、
その間も操作は止まらない)。

`l` / `→` / `▸` をクリック
                          枝を開く
`h` / `←` / `▾` をクリック
                          枝を閉じる(`h` と `←` は、開いていない行では 1 段上
                          の枝を閉じる)
`L`                       その行から下を、3 段下までまとめて開く。呼び出し元は
                          段ごとに増えるので、300 行を足したところで止め、止め
                          たことを行に出す(`opened until 300 rows`)
`Enter` / ダブルクリック  その行の呼び出しがある場所へ移る(呼び出し元なら、そ
                          の関数の中で呼んでいる行)。名前を 1 回クリックしただ
                          けでは、カーソルが移るだけ
`gd`                      その行の関数の定義へ移る
`t`                       呼び出し元と呼んでいる先を切り替える

行の右端に出るのは、呼び出しがある場所。名前の後ろには、次の印が付く。

`×3`                      3 か所(3 行)から呼んでいる
`↻`                       上にすでに出ている関数(再帰)。それ以上は開かない
`macro`                   マクロ。呼び出し元の向きでは開けて、そのマクロを使っ
                          ている関数をたどれる。呼んでいる先の向きでは、マクロ
                          の中身は読まないので開かない
`not in GTAGS`            定義が GTAGS に無い名前(ライブラリの関数、関数ポイン
                          タなど)
`+2 of this name`         同じ名前の定義がほかに 2 つある(別のファイルの
                          static 関数など)。呼んでいる関数と同じファイルにあれ
                          ば、そちらを選ぶ
`no callers` / `calls nothing`
                          開いたが、何も見つからなかった

呼び出し元は、`global -r` の結果を、それぞれがどの関数の中にあるかでまとめたも
の。どの関数の中かは、ファイルの構文を解析して決める。`#ifdef` のせいで構文が
読めなくなった部分では、1 桁目の `{` と `}` から関数の範囲を決める(vim の `[[`
と同じ考え方)。プロトタイプ宣言(`int f(int);`)は呼び出しではないので出さない。
呼んでいる先は、関数の本体にある呼び出しを構文から拾い、定義の場所を
`global -d` で引く。

何が何を呼ぶかを調べる部分は、パネルと分けてある(`lua/taka/call_tree/`)。
`lua/taka/call_tree/init.lua` の先頭に、調べる部分が満たす約束(関数 3 つと、ノー
ドの形)が書いてある。今あるのは GTAGS(`gtags.lua`)と、言語サーバーの呼び出し階
層(`lsp.lua`、`callHierarchy/incomingCalls` など)の 2 つで、GTAGS の無いファイ
ルでは言語サーバーが答える(|cfg-lsp|)。

gtags と同じく名前で探すので、次のものは正しく出ない。

- 関数ポインタを通した呼び出し
- 別のファイルにある同じ名前の static 関数(区別できずに混ざる)
- マクロの中身で呼んでいる関数(呼んでいる先には出ない)

日本語を含むソース (Shift-JIS / EUC-JP)                         *cfg-encoding*

Neovim の既定の `fileencodings` は `ucs-bom,utf-8,default,latin1` で日本語の項
目を持たないため、cp932 のコメントが文字化けする。`lua/config/options.lua` で
cp932 を判定順に加えてある。

cp932 (Shift-JIS)         できる
UTF-8 / BOM 付き UTF-8 / UTF-16
                          できる
判定不能なバイト列        latin1 として開く(バイト列は壊れない)
EUC-JP                    漢字を含めば通ることが多いが、対象外(下記)

EUC-JP を候補に入れていないのは、EUC-JP のひらがなが cp932 の半角カタカナとし
ても正当なバイト列で、漢字を含まない EUC-JP ファイルを cp932 と誤判定するため。
使わない候補は誤判定の可能性を増やすだけなので外している。遭遇したら
`:e ++enc=euc-jp` で開き直すか、`options.lua` の `cp932` の後ろに `"euc-jp"`
を足す。

UTF-8 以外のバッファは、ステータスラインにエンコーディング名が警告色で出る。
cp932 が表現できない文字(絵文字や他コードページ由来の記号)を打つと、編集時では
なく `:write` の瞬間に `E513` で保存に失敗するため、その予告として表示している。

判定を間違えたファイルは `:e ++enc=cp932` のように明示して開き直す。

ctags フォールバック (gutentags)                                   *cfg-ctags*

gtags は C/C++/Java など主要言語以外をほぼ取りこぼす。C コードでも Shift-JIS
エンコーディングや非標準拡張子で動かないケースがある。そういう時のために
vim-gutentags + ctags モードを併設している。

------------------------------------------------------------------------------
動き方                                                         *cfg-ctags-how*

- `<leader>jB` で `tags` を作る。開いているファイルを gutentags がプロジェクト
  とみなしていれば(バージョン管理されているディレクトリ、または空の
  `.gutctags-root` を置いたディレクトリ)、gutentags 経由でそのルートに作る。そ
  れ以外 — ファイルを開いていない、展開しただけのソースツリー、複数のチェック
  アウトを並べた親ディレクトリ — では `ctags -R` を直接バックグラウンドで実行
  し、`GTAGS` のあるディレクトリ、無ければ cwd に作る(cwd のときは場所を表示し
  て確認する)
- 保存時に自動で更新されるのは、gutentags 経由で作った `tags` だけ。直接作った
  `tags` は `<leader>jB` で作り直す。展開しただけのツリーでも自動更新したけれ
  ば、ルートに空の `.gutctags-root` を置く
- `tags` はプロジェクトのルートに出来る。Vim は設定なしでも上の階層へ `tags`
  を探しに行くので、gutentags の無い環境や他のツールからも同じファイルが使える。
  `GTAGS` と同じ場所でもある。検索結果には混ざらない(`ripgreprc` で除外してい
  る)。git 管理のツリーでは未追跡ファイルとして見えるので、個人のグローバル
  gitignore に `tags` を入れておく
- 索引はバックグラウンドで走り、その間ステータスラインにスピナーと
  `ctags: indexing`、1 秒を超えると経過秒数が出る。終わると所要時間が 2 秒表示
  され、3 秒以上かかった索引は通知でも知らせる
- 以後はファイル保存のたびに差分更新
- 何もしなければ tags は作られない。複数のソースツリーを並べただけの親ディレク
  トリで巨大な tags を作ってしまう事故を防ぐため、自動生成は無効にしてある
- 除外したいディレクトリなど、マシン固有の設定は `lua/config/local.lua`(git 管
  理外)に書く。例:

>
    vim.g.gutentags_exclude_project_root = { vim.fn.expand("~/src/all-projects") }
<
- 定義ジャンプ(`<C-]>` / `Ctrl+クリック`)は gtags が空振りすると自動で ctags
  にフォールバックするので、gtags で引ける箇所は gtags、引けない箇所は ctags、
  と透過的に切り替わる。ctags 側で候補が複数あるときも、Vim 標準の番号選択では
  なく、gtags のときと同じピッカーが開く
- タグ名は大文字小文字を区別して照合する(`tagcase=match`)。LazyVim の
  `ignorecase` のままだと `SSL_new` と `ssl_new` を同じタグとみなし、ジャンプ
  のたびに候補選択で止まる
- エディタのローカル履歴(`.history/`)やバックアップ、他ツールの索引ファイルは
  ctags の索引から除外している。古いコピーが索引に入ると、フォールバック時にそ
  ちらへ着地するため

------------------------------------------------------------------------------
注意点                                                       *cfg-ctags-notes*

- vim-gutentags 付属のバッチは、ログファイルを渡されないと進行状況をコンソール
  (`CON`)に直接書く。nvim のパイプを通らないので、そのままだと索引のたび、保存
  のたびに画面の上に文字が乗る。`bin/gutentags/update_tags.cmd` が、出力先を
  `NUL` にして元のバッチを呼び直している
- Strawberry Perl 同梱の Exuberant Ctags 5.8 (2009) は使わない。
  `winget install universal-ctags.ctags` で Universal Ctags を入れ、PATH 優先
  度を上げる
- Shift-JIS ソースを扱う場合は、Universal Ctags なら
  `--input-encoding=shift_jis` を `~/.ctags.d/*.ctags` で指定可能
- gtags でも動かない・ctags でも動かない言語の場合は、ファイル拡張子のマッピン
  グ(`--langmap`)を ctags 設定に追加する必要がある

SVN (Subversion)                                                     *cfg-svn*

`<leader>g` が git、`<leader>v` が SVN。SVN の操作は読み取りだけで、コミット・
更新・ファイルの取り消しはこの設定からは実行しない。唯一書き換えるのはハンクの
取り消しで、バッファに対して行い、確認を挟む(保存するまでファイルは変わらず、
`u` でも戻せる)。

行番号の横の印  最後に `svn update` した版 (BASE) からの追加・変更・削除
                (vim-signify)。見た目は git のファイルの印と同じで、追加は緑、
                変更は青の縦棒、削除は赤い三角(2 行以上消したときは行数)。比較
                はローカルの `.svn` に対して行い、サーバには問い合わせない
`]h` / `[h`     次 / 前の変更箇所へ。git の checkout では gitsigns の同じキー
                が効く
`<leader>vs`    cwd 以下の `svn status` を quickfix に出す。ファイルツリーの中
                で押すと、選んでいるフォルダ(ファイルならそのフォルダ)以下が対
                象になる。状態(modified など)を左の列に色付きで出し、変更のあ
                るものを上、バージョン管理外のものを下に並べる。Enter でそのフ
                ァイルを開く
`<leader>vS`    フォルダのパスを入力して、その下の `svn status` を出す。ファイ
                ルツリーでフォルダを選んで押すと、そのフォルダが入力済みの状態
                で聞かれる
`<leader>vd`    今のファイルを BASE と左右に並べて比較する。左の窓の上に
                `BASE`、右に `working copy` と見出しが出る。どちらの窓でも `q`
                で比較を終える
`<leader>vh`    今のファイル、またはファイルツリーで選んだファイル・フォルダの
                `svn log` を、専用のタブに出す(TortoiseSVN のログ画面と同じ流
                れ)。右のリストでリビジョンを Enter・`l`・ダブルクリックで開く
                と、コミットメッセージの続きと、そのリビジョンで変わったファイ
                ルがリポジトリ全体から出る(`h` で閉じる)。ファイルを Enter か
                ダブルクリックすると、その変更が左に左右に並び、最初の変更箇所
                に移る。左右の窓の上には、どのリビジョンかの見出しが出る(左:
                一つ前のリビジョンとパス、右: そのリビジョン、作者、日付、コミ
                ットメッセージの 1 行目)。次のファイルを選ぶと入れ替わる。ファ
                イルは名前を先に、フォルダを後ろに薄く出す(パスが長くても、切
                れるのはフォルダの側)。見ている場所の外のファイルは、全体を薄
                くして、フォルダをリポジトリのパスで出す。タブのどの窓でも `q`
                を押すと、タブごと閉じる
`<leader>vb`    その行を、誰が、いつ、どのリビジョンで書いたかを、左の細い窓に
                1 行ずつ出す(TortoiseSVN の Blame と同じ)。もう一度押すか、そ
                の窓で `q` を押すと閉じる。押したときだけ裏で `svn blame` を走
                らせ、答えを覚えておくので、`svn update` するまでは 2 回目から
                待たない。窓のファイルを切り替えると、blame もそのファイルのも
                のに替わる(SVN の外のファイルでは、そう出る)。`svn update` の
                後に編集した行や足した行は `(local)` と出し、ほかの行は、上に
                行を足して位置がずれても、そのリビジョンが出る。カーソルのある
                行と同じリビジョンの行は、左の窓では背景に、ファイルでは行番号
                に色が付く。スクロールでカーソルが押されて動いても、色は元のリ
                ビジョンに残る。どちらかの窓でカーソルを動かすと、もう片方も同
                じ行へ動き、どちらをスクロールしても行がそろったまま動く。窓の
                行で `Enter` を押すと、そのリビジョンのコミットメッセージが出
                る
`<leader>vp`    カーソル位置の変更を小窓で見る
`<leader>vr`    カーソル位置の変更を BASE に戻す(確認あり)

- リビジョンは URL とペグリビジョン (`url@rev`) で取り出すので、その後に削除・
  改名されたファイルも表示できる。そのリビジョンで追加・削除されたファイルは、
  存在しない側を空にして並べる
- `svn status` の一覧では、バージョン管理外のドットファイル・ドットフォルダ
  (`.vs` や `.cache` など、ツールの状態)を出さない。バージョン管理下のものは出
  る
- `svn` コマンドが PATH に要る。TortoiseSVN だけでは `svn.exe` が入らないこと
  があるので、インストーラで command line client tools を有効にする。無い環境
  では vim-signify を読み込まず、`<leader>v` のキーも作らない(SVN を使わない
  PC では、何も入っていないのと同じ)。この判定は起動時に行うので、`svn` を入れ
  た後は nvim を起動し直す
- 変更の印には `diff` プログラムが要る。Git Bash には PATH に入っているが、
  PowerShell や cmd には無い。その場合は Git for Windows に同梱の
  `usr\bin\diff.exe` を自動で使う。どちらも見つからないときは、起動時に一度だ
  け知らせる
- 印はファイルを開いたときと保存したときに更新される。エディタの外で
  `svn update` した後は、ファイルを開き直す
- `bin\test.cmd` は、`svn` と `svnadmin` がある環境でだけ、印・status・ログの
  タブ(リビジョンで変わったファイルの一覧、見ている場所の外のファイル、変更・
  追加・削除の左右比較、閉じるとタブも閉じること)・ハンクの取り消しを確かめる。
  無い環境ではスキップになる。`svn` が PATH に無いときに vim-signify も
  `<leader>v` も現れないことは、どちらの環境でも確かめる
