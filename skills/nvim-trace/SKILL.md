# nvim-trace

利用者の Neovim は、トレースファイル（1 行 1 手順の JSON Lines）を読んで、
コードの各行の上に見出しと解説を重ね、右のパネルに手順を木の形で並べる。
ファイルが書き足されるとその場で表示が増えるので、**調べながら 1 手順ずつ追記する**。

## 置き場所

Neovim のデータディレクトリの下の `traces/<内容が分かる名前>.jsonl`。

- Windows: `%LOCALAPPDATA%\nvim-data\traces\`
- macOS / Linux: `~/.local/share/nvim/traces/`
- 確かめるには `nvim --headless -c "lua io.stdout:write(vim.fn.stdpath('data'))" -c q`
- フォルダが無ければ作る

ファイルの扱い:

- 調査 1 件につき 1 ファイル。名前は英小文字とハイフン（例: `srtp-crash.jsonl`）
- 同じ調査の続きなら同じファイルに追記する。別の調査なら新しいファイルにする
  （同じプロジェクトの新しいファイルができると、表示は自動でそちらに切り替わる。
  ただし利用者が一覧から別のトレースを選んで見ている間は切り替わらないので、
  新しいトレースを作ったら「`<leader>jA` で選べる」と伝える）
- トレースのフォルダは全プロジェクトで共通。Neovim は見出しの `root` で、どの
  プロジェクトのトレースかを分ける（一覧や自動の切り替えは、利用者が今開いている
  プロジェクトのものだけになる）。だから `root` は必ず書く
- **調べているソースには何も書き込まない**（作業コピーを汚さない）

## どのトレースのことか

トレースはファイル名（拡張子を除いたもの、例: `pem-header-double-free`）を名前として
呼ぶ。番号は付けない。

- 新しく作ったら、チャットで名前を伝える（「`pem-header-double-free` に書いた」）
- 利用者は `Trace "pem-header-double-free" step 10/12: …` のように名前を貼ってくる
  （パネルや一覧の `y` でコピーしたもの）。その名前のファイルを使う
- 「PEM の二重解放のトレース」のように言葉で頼まれたら、トレースのフォルダの
  各ファイルの 1 行目（見出しの `title`）を探して当てる。候補が 1 つに決まらなければ、
  候補の名前と見出しを並べて利用者に聞く
- 続きを頼まれたら、先にそのファイルを読んでから追記する

## 書き方

1 行目は見出し（`line` を持たない行）:

```json
{"title": "SRTP の拡張で落ちる経路", "root": "<調べているリポジトリの絶対パス>"}
```

`root` は、調べているプロジェクトの根元（`.git`・`.svn`・`GTAGS` のあるフォルダ）の
絶対パス。サブフォルダを書くと、プロジェクトの根元で開いている利用者からも見えるが、
根元を書くのがいちばん確実

その後、手順を 1 行ずつファイルの末尾に足す。**ファイルは末尾に足すだけにし、全体を書き直さない**
（利用者が書き換えた手順が消えるため）。次の例の `text` は形を示すためのもの:

```json
{"id": "entry", "file": "ssl/statem/extensions_srvr.c", "line": 120, "text": "if (!tls_parse_ctos_use_srtp(s, pkt, context, x, chainidx))", "title": "拡張を読むところ", "note": "use_srtp 拡張があるとここに来る。"}
{"id": "len", "parent": "entry", "file": "ssl/d1_srtp.c", "line": 60, "text": "len = strlen(ptr);", "title": "len の計算", "note": "col が NULL のとき ...", "kind": "cause"}
```

| キー | 中身 |
|---|---|
| `file` / `line` | 必須。`root` からの相対パスか絶対パス。`line` は 1 始まりで、**実際にファイルを開いて確かめた行番号** |
| `text` | **必ず書く**。その行に書いてあることを、ファイルから写す（行全体か、8 文字以上の特徴的な一部）。行番号がずれていても、表示側がこれで正しい行を探し直す。見つからないと警告が出るので、行番号の書き間違いにも気づける |
| `title` | パネルに出る見出し。20 字前後で「何をする所か」 |
| `note` | その行の上に出る解説。改行は `\n`。長くても窓の幅で折り返される |
| `kind` | `cause`（原因と確定）/ `suspect`（怪しいが未確定）/ `answer`（問い合わせへの結論）/ 省略（普通の手順） |
| `id` | 各手順に付ける短い名前（英数字）。手順を見分けるのに使う |
| `parent` | 枝分かれするときだけ使う。別の手順の `id` を書くとその下に付く。省略すると最上位に、書いた順で並ぶ |

ファイルの書き方の決まり:

- JSON は 1 手順 1 行で、途中に改行を入れない。**各行の最後に改行を付ける**（無いまま
  次を足すと 2 つの手順が 1 行につながり、両方とも読めなくなる）
- 文字コードは **BOM なしの UTF-8**。日本語などはそのまま書く。Windows PowerShell 5 の
  `>>` や `Out-File` は UTF-16 で書くので使わない
- JSON は手で組み立てず、言語の JSON 出力機能で作る（例: Python の
  `json.dumps(obj, ensure_ascii=False)`）。解説に `"` や `\` が入っても壊れない

見出しと解説は、利用者が話している言語で書く。

## 検査

書き終えたら（長いトレースなら書いている途中でも）、Neovim がパネルに出すときと同じ
読み方で検査する。結果は標準出力に出て、問題の数が終了コードになる:

```
nvim --headless -c "lua require('taka.trace').check_and_exit([[<トレースファイルの絶対パス>]])"
```

```
srtp-crash.jsonl: 12 steps, 2 problems
line 5: not JSON
line 8, step 6 (d1_srtp.c:60): the text is on line 63, not on line 60
```

- 1 行目が `0 problems` になるまで直して検査し直す。問題が残ったまま「できた」と言わない
- `the text is on line X, not on line Y` は行番号の誤り。ファイルを読み直して確かめ、
  正しい行番号の手順を書き直す（このときだけは、利用者が書き換えていない自分の手順の
  行を、正しい内容の行に置き換えてよい）
- 検査で分かるのは形と行の正しさまで。解説の中身が正しいかは分からないので、
  中身は自分で読み直して確かめる

## 仕様の問い合わせに答えるとき

「X のとき Y になるか」「この設定は何に効くか」のような問い合わせに答えるために、
処理の流れを調べるときは、次の形にする。利用者は結論と根拠を自分で読んで確かめ、
パネルの `Y`（トレース全体を Markdown でコピー）で回答の下書きにする。

- 見出し行の `title` は、問い合わせそのもの（例: 「接続が切れたとき再送は何回か」）
- **1 番目の手順を結論にする**（`kind: "answer"`）。振る舞いが決まる行に置き、`note` に
  条件付きの答えを書く（「既定では 3 回。環境変数 X があればその値」）。言い切れない
  ところは言い切らない
- そのあとに、結論の根拠を処理の順に並べる。答えを左右する分岐の条件、設定の読み込み、
  既定値の出どころは、必ずそれぞれ手順にする
- コードだけでは決まらない前提（実行時の設定値、外部からの入力、別のモジュールや
  ライブラリの振る舞い）は `suspect` にし、何を確かめれば確定するかを `note` に書く
- チャットでは、結論と、人が確かめるべき点だけを言う

## 利用者による書き換え

利用者は、手順の見出し（`title`）と解説（`note`）を自分の言葉に書き換えることがある。
書き換えた手順の行には `"edited": true` が付く。

- `edited` の手順は利用者の考え。消さない・書き換えない
- そのトレースの続きを頼まれたときは、先にファイルを読み、`edited` の手順を確かめる。
  利用者の書いたことがコードと食い違っていれば、チャットで指摘する。
  調べ直して分かったことは、新しい手順として末尾に足す

## 手順の選び方

- 読む人は、自分では全体を読み解けない前提で書く。**入口から原因（解説なら終わり）まで、
  読む順に**並べる（呼び出しの順、データが流れる順）
- 1 手順 = 1 か所。「この行で何が起きて、なぜ次の手順に行くのか」を `note` に書く
- 本筋は最上位に順番に並べる。脇道は本筋の途中に挟まない
  （次の手順へ進むキーは、パネルの並び順に進むため）。脇道の置き方は 1 つの判定で決める:
  **読んだあと親の行に戻るなら `parent` で枝に、戻らないなら本筋の後ろに**
  - 枝（字下げ）= 上の行から潜って見たもの。呼んでいる関数の中で何が返るか、値の出どころ、
    構造体の定義。読み手は親の行に戻って本筋を続ける
  - 末尾 = 本筋と並行する別の線。別の呼び出し元、無事だった方の分岐、確かめたが関係なかった所。
    本筋を読み終えてから見る
- 原因が確定したら `kind: "cause"`。確信が無い所は `suspect` にし、根拠と不確かさを `note` に書く
- 行番号を推測で書かない。検索や定義ジャンプの道具で見つけ、ファイルを読んで行を確かめてから書く。
  `text` はそのとき読んだ行から写す（記憶から書かない）
- 書き終えたら、必ず検査する（「検査」の節）
- 調べ終えたら、チャットでは要約と結論だけを言う（詳細はトレースにあるので繰り返さない）
